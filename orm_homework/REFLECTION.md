# Рефлексія. Заняття 36. SQLAlchemy ORM

## Що я навчився?

- Навіщо потрібен ORM: не "менше коду заради коду", а те, що бізнес-логіка перестає знати, яким саме SQL вона виражена — `models.py`'s 11 функцій і сигнатура, і поведінка лишились ідентичними, а `expense_tracker/`/`main.py` не змінились жодним рядком.
- Моделювання через Declarative (`Mapped`/`mapped_column`) і що анотація типу — не просто підказка для IDE, а те, що SQLAlchemy реально резолвить під час визначення класу (звідси `str | None` падав на Python 3.9 — довелось перейти на `Optional[str]`).
- `relationship()`/`back_populates`, і що eager loading (`joinedload`/`selectinload`) — не "магія швидкості", а явний вибір: один JOIN-запит проти N+1 окремих.
- Що CRUD через ORM — це не завжди коротше: корельований підзапит у `get_budget_limits`/`check_budget_status` (порівняння категорій без врахування регістру) через `aliased()` і `scalar_subquery()` вийшов не простішим за сирий SQL, просто типобезпечним.

## Найскладніший момент

Перенести вже наявну, добре протестовану (160+ тестів) функціональність на ORM так, щоб жодна поведінка не змінилась — особливо `get_budget_limits`/`check_budget_status` із корельованим підзапитом і порівнянням `LOWER(name)` з обох боків. Довелось будувати підзапит через `aliased(Category)` + `scalar_subquery()`, акуратно звіряючи з оригінальним SQL рядок у рядок.

## Еврика-момент!

Що перехід на `LIKE`-префікс замість Postgres-специфічного `SUBSTRING()` у `check_budget_status` виявився не компромісом, а покращенням: той самий код тепер працює і проти SQLite (`orm_homework/test_models_sqlite.py`), без жодної спеціальної гілки для різних БД. Ось де ORM реально себе виправдав — не менше коду, а код, що переживає зміну рушія бази даних.

## Порівняння SQL vs ORM

Для простих CRUD (`create_user`, `get_username_by_email`) — ORM однозначно читабельніший і безпечніший (типізація, autocomplete, захист від SQL-ін'єкцій за замовчуванням). Для складних агрегацій з корельованими підзапитами (`get_budget_limits`) — приблизно нарівні з сирим SQL за складністю, виграш лише в переносимості між СУБД, а не в кількості рядків.

## План на Django

Очікую, що Django ORM буде простішим для "типових" CRUD-сценаріїв (менше boilerplate для сесій/engine), але складніші корельовані підзапити, ймовірно, доведеться або виражати через `.raw()`/`Subquery`, або прийняти N+1 і оптимізувати через `select_related`/`prefetch_related` — підозрюю, що ті самі компроміси, просто інший синтаксис.
